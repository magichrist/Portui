## BUG-001 — Theme switching is visually broken (baked CSS variables shadow dynamic ones)

- Category: functional / UI correctness
- Severity: HIGH
- Priority: P1
- Confidence: HIGH (reproduced headlessly)
- Status: FIXED

### Summary
`Ctrl+T` / `T` / `--theme` do not reliably change the rendered palette. CSS-variable-driven
colors (backgrounds, borders) stay on the import-time palette, and inline `Rich.Text` styles
stay on the pre-switch palette. The advertised "six themes, switchable live" feature is
effectively non-functional.

### Root cause
1. `config.with_tokens()` prepends literal `$name: #hex;` declarations into every widget's
   `DEFAULT_CSS` at **import time**. `src/ports_explorer/styles/app.tcss` also declares the
   full variable set at lines 7–22 with **midnight's** values.
2. Textual's `substitute_references()` uses `variables.setdefault(name, [])` and then
   *appends* CSS-declared values to the app-level variables supplied by
   `App.get_css_variables()`. The CSS declaration therefore wins (last color token).
   Result: app.tcss rules always resolve to the hardcoded midnight palette, and widget
   DEFAULT_CSS rules resolve to the palette that was active when the module was imported.
3. `app.apply_theme()` calls `refresh_css()` + `_refresh_visible_content()`, but the latter
   only calls `render_overview`/`render_detail`. `AppHeader`, `ScreenBanner`, `EmptyState`,
   `ResourceTable`, `HealthBadge` etc. have neither, so their inline `Text` styles keep the
   old palette's hex colors.
4. `app.py:103` calls `self.screen.query_one("StatusBar").refresh_content()` — `StatusBar`
   has no `refresh_content()` method. The call is wrapped in `with suppress(Exception)`, so
   it silently does nothing (the method exists only on `EmptyState`, `common.py:402`).

### Evidence (headless probes)
- Start with gummy, switch to daylight: `#header-title` first span stays `rgb(255,92,138) bold`
  (gummy coral) instead of daylight's `rgb(194,24,91)`.
- Start with gummy, switch to daylight: screen background stays `Color(20,18,27)` even though
  `app.stylesheet._variables["surface"] == "#FAFAFA"`.
- Start with `--theme daylight`: header text is daylight coral, but screen background stays
  midnight `Color(20,18,27)` and a `Metric` tile background stays gummy `Color(30,21,38)`.

### Impact
- Users see a notification "Theme: Daylight" while the UI remains in the old palette.
- `--theme NAME` only changes inline text, not surfaces/borders.

### Recommendation
- Remove all `$name: #hex;` declarations from `app.tcss` (keep only `var()` references) and
  stop baking values via `with_tokens()` — let `get_css_variables()` be the single source.
- Replace `with_tokens()` with a no-op or make it emit only the CSS body.
- In `_refresh_visible_content()`, explicitly re-render `AppHeader`, `ScreenBanner`,
  `EmptyState`, `ResourceTable` cells, and give `StatusBar` a real `refresh_content()`
  (or call `set_counts`/`set_keys`/`set_health` again).
- Add a headless test asserting rendered colors change after `apply_theme()`.

### Affected files
`config.py` (with_tokens), `styles/app.tcss` (lines 7–22), `app.py` (70–103),
`screens/common.py` (AppHeader, ScreenBanner, EmptyState), `widgets/*`.

## BUG-002 — "UNIQUE NETWORK"/"LISTENING" metrics count raw, not deduplicated records

- Category: logic / data correctness
- Severity: MEDIUM
- Priority: P2
- Confidence: HIGH
- Status: FIXED

### Summary
The process-detail overview and status bar show counts computed from `CollectionResult.records`
(raw lsof rows), while the tabs show deduplicated rows. Duplicate FDs inflate the numbers.

### Root cause
`models.CollectionResult.network_count/listener_count/file_count` iterate `self.records`
(raw). `screens/process_detail.py:312–314` displays them under labels "UNIQUE NETWORK",
"LISTENING", "OTHER RESOURCES", and `_apply_status()` (lines 499–503) does the same.
Only the collection note uses `len(self._deduped)`.

### Evidence
Fixture `lsof_duplicate_fds.txt` (3 FDs → 1 unique socket):
`result.listener_count == 3`, `result.network_count == 3`, but `len(deduplicate(records)) == 1`.
The Listening tab shows 1 row while the metric says 3.

### Impact
Contradicts the README's honesty claim ("reports raw and unique counts") and can make a
single listening socket appear as three.

### Recommendation
Compute counts from `self._deduped` for display (or add dedup-aware count properties and
label the raw numbers explicitly as "raw").

### Affected files
`models.py:357–367`, `screens/process_detail.py:312–314, 499–503`.

## BUG-003 — `fd=N` field search uses substring matching and returns wrong FDs

- Category: search correctness
- Severity: MEDIUM
- Priority: P2
- Confidence: HIGH
- Status: FIXED

### Summary
`search_resources(..., "fd=1")` matches FDs 10, 11, 12, … because `_field_hits()` does
`value in record.fd.lower()` instead of an exact numeric comparison. `pid=N` correctly uses
`== int(value)`, so behavior is inconsistent.

### Evidence
`search_resources(parse_lsof_output(lsof_duplicate_fds.txt)[0], "fd=1")` → FDs `['10','11','12']`.

### Recommendation
`case "fd": return value.isdigit() and int(record.fd) == int(value)` (with a fallback for
non-numeric descriptors like `cwd`, `txt`).

### Affected files
`services/resource_search.py:164–167`.

## BUG-004 — Quoted `key="value with spaces"` searches silently fail

- Category: search correctness
- Severity: MEDIUM
- Priority: P2
- Confidence: HIGH
- Status: FIXED

### Summary
Free-text quoted phrases work (`"/Users/me/My Folder/file"`), but `path="..."`, `name="..."`
etc. do not, because `tokenize()`'s `"[^"]+"|\S+` regex cannot treat a quote that appears
mid-token as the start of a quoted phrase.

### Evidence
For `/Users/dev/My Projects/data with spaces/file.txt`:
- `tokenize('path="/.../data with spaces/file.txt"')` → `['path="/Users/dev/My', 'Projects/data', 'with', 'spaces/file.txt"']`
- `search_resources([rec], that_query)` → `[]`
- `search_resources([rec], '"/.../data with spaces/file.txt"')` → `[rec]`

### Impact
Documented "Quote phrases for paths with spaces" fails whenever a field filter is used —
the most likely case for paths. `ResourceBrowserScreen._filter_from_tokens()` also splits on
`str.split()`, breaking the same input.

### Recommendation
Use a tokenizer that handles `key=value` where value may be quoted, e.g.
`(?P<key>[a-z]+)=(?P<q>"[^"]*"|\S+)|"(?P<phrase>[^"]+)"|(?P<bare>\S+)`.

### Affected files
`services/resource_search.py:24, 47–60, 151–189`, `screens/resource_browser.py:32–65`.

## BUG-005 — `k`-arm has no scheduled timer; "5s" expiry is lazy only

- Category: state/lifecycle / safety-adjacent UI
- Severity: MEDIUM
- Priority: P2
- Confidence: HIGH
- Status: FIXED

### Summary
`KillMixin` declares `_kill_timer` and `_disarm_kill()` stops it, but `_arm_kill()` never
schedules a timer. The 5-second window is only enforced lazily by `_kill_expired()` on the
next `k` press. The status bar hint therefore stays at "TERMINATE armed · k to confirm in 5s"
(soon showing `0s`) indefinitely until another key is pressed, and the user can remain in a
visibly armed state long after the documented window.

### Root cause
`common.py:199–211` sets `_kill_deadline` but never assigns `self._kill_timer = self.set_timer(...)`.
Grep confirms `_kill_timer` appears only at lines 168, 189, 193.

### Impact
Misleading UI and a mismatch with README ("waiting 5 seconds cancels it"). The hard safety
contract is still upheld (a stale arm re-arms instead of firing), so no accidental kill.

### Recommendation
Schedule `self._kill_timer = self.set_timer(ARM_TIMEOUT, self._disarm_kill)` in `_arm_kill()`.

### Affected files
`screens/common.py:165–211`.

## BUG-006 — `CancelledError` not handled in exclusive workers; transient stuck status

- Category: async correctness
- Severity: LOW
- Priority: P3
- Confidence: MEDIUM
- Status: FIXED

### Summary
`ProcessListScreen.collect_processes()` and `ProcessDetailScreen.collect_resources()` set
`_loading`/`_collecting = True` before awaiting, and only catch `Exception`. `asyncio.CancelledError`
inherits `BaseException`, so cancellation by a newer exclusive worker (same group) skips the
reset. A slow snapshot at a 2s tick can leave the status bar showing "Collecting…" until the
next successful worker.

### Recommendation
Wrap the await in `try/finally` (or add `except asyncio.CancelledError: raise` with cleanup)
so flags and status are always reset.

### Affected files
`screens/process_list.py:172–190`, `screens/process_detail.py:359–391`.

## BUG-008 — Live process with zero lsof rows is mislabeled "permission denied"

- Category: honesty / diagnostics
- Severity: LOW
- Priority: P3
- Confidence: MEDIUM
- Status: FIXED

### Summary
`_classify_permission()` maps `records == [] and process_exists` to `PermissionState.DENIED`
unconditionally. A live process that genuinely has no visible descriptors is reported as a
permission problem rather than an empty inventory. Conversely a zombie is also treated as
alive here. Conflicts with the README's "stated, never faked" promise.

### Recommendation
Add a distinct "no descriptors" state (or check stderr/exit code more carefully) instead of
defaulting to DENIED; treat zombies as gone.

### Affected files
`collectors/lsof.py:395–423`.
